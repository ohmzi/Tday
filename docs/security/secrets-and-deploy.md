# Secrets & deployment procedure

How to generate every secret T'Day needs, set it on the deploy host, and roll out changes safely.

> **Never commit a real secret.** `.env` and `.env.docker` (and any copy like `.env.docker.bak`,
> `.env.prod`) are gitignored. Only `.env.example`, which holds placeholders, is tracked.
> Verify any new file before committing: `git check-ignore -v <file>`.
>
> Nothing in this document contains a real key. Every value below is generated by you, on the
> machine that will use it.

---

## 1. The two secrets that must be set

| Variable | Required? | What it does | Rotating it costs |
|---|---|---|---|
| `AUTH_SECRET` | **Yes** — the backend refuses to boot without it | Derives the JWE session key, and the HMAC key for throttle buckets | Everyone is signed out; persisted rate-limit buckets are orphaned |
| `DATABASE_URL` | **Yes** — refuses to boot without it | Postgres connection | n/a |
| `DATA_ENCRYPTION_KEY` | **No — optional, off by default** | Encrypts task titles, descriptions and webhook secrets at rest | Rows written with the old key become unreadable unless you keep it in `DATA_ENCRYPTION_KEYS` |

All live in `.env.docker` on the deploy host.

Only the first two are mandatory. Leaving `DATA_ENCRYPTION_KEY` empty is a supported setup — see §4.

## 2. Generate them

Run these **on the machine that will use them** so the value never travels over chat, email or a
clipboard sync:

```bash
openssl rand -base64 32
```

Run it once per secret — they must be different values. `AUTH_SECRET` accepts any string ≥ 16
characters (see §6 for why that floor matters). `DATA_ENCRYPTION_KEY` must decode to exactly 32
bytes, so **use the `openssl rand -base64 32` form for it specifically** — a 32-byte base64 string
or a 64-character hex string. Anything else is rejected at boot.

## 3. Set them on the deploy host

```bash
ssh <user>@<deploy-host>
cd /path/to/Tday

cp .env.docker ".env.docker.bak.$(date +%F)"   # covered by .gitignore
```

Edit `.env.docker` and set:

```bash
AUTH_SECRET=<paste the first generated value>
DATA_ENCRYPTION_KEY=<paste the second generated value>
DATA_ENCRYPTION_KEY_ID=primary
TDAY_ENV=production
```

`TDAY_ENV=production` is not optional. It is what enables HSTS, the `__Secure-` cookie prefix and
the `Secure` cookie flag. In any other value those protections silently do nothing.

Then apply:

```bash
docker compose up -d --build tday-backend
docker compose logs -f tday-backend      # watch it actually come up
curl -sf http://127.0.0.1:2525/health    # expect {"status":"ok"}
```

There is no required ordering between setting secrets and deploying — see §4 for why.

## 4. Encryption at rest is optional (and off by default)

Leaving `DATA_ENCRYPTION_KEY` empty is a **supported configuration**. The server boots and logs one
line stating that task titles and descriptions are stored as plaintext in Postgres.

That is a defensible trade on a single-operator box: anyone who can read the database already has
the host, and the key would be sitting in the same `.env.docker` right next to the Postgres volume.
Field encryption does not defend against host compromise and never claimed to.

**What it does defend against is a database dump that leaves the host** — copied to a NAS, synced to
cloud storage, restored on a laptop. For that threat, [encrypting your backups](backups.md) is the
better control: it protects the copy that actually travels, and it cannot take your server down.

If you do want the guarantee enforced:

```bash
DATA_ENCRYPTION_KEY=<32-byte base64>
REQUIRE_ENCRYPTION_AT_REST=true
```

With that set, a missing or malformed key becomes a hard startup failure — deliberately, because
that is the case where you would rather the server not start than write plaintext. Without it, a
missing key can never strand you.

Two things to know either way:

- **Encryption is not retroactive.** Turning it on encrypts *new* writes. Existing rows stay
  plaintext until they are next saved. Mixed state is safe — `decryptIfEncrypted` passes plaintext
  through — but existing content is not protected retroactively.
- **Do not lose the key.** Rows written with it are unreadable without it. During rotation keep the
  old key in `DATA_ENCRYPTION_KEYS` until everything has been rewritten.

## 5. Rotating `AUTH_SECRET` (do this once, deliberately)

A real `AUTH_SECRET` was committed to this repo's **public** git history in its first commits. Git
history is permanent, so rotation — not history rewriting — is the fix.

Check whether the host still uses the leaked value:

```bash
ssh <user>@<deploy-host> \
  "grep '^AUTH_SECRET=' /path/to/Tday/.env.docker | cut -d= -f2- | head -c 6"
```

If that prints `XM58Ay`, rotate immediately: generate a new value (§2), set it (§3), restart.
Everyone is signed out and signs in again — that is the intended effect. Do it when you have your
admin password to hand.

Rotate `CRONJOB_SECRET` too if present — or better, delete the line: nothing in the codebase reads
it. Same for the `AUTH_CAPTCHA_*` block.

## 6. Things that fail quietly

- **`AUTH_SECRET` shorter than 16 characters.** It is required to boot but its length is never
  validated. Below 16 the app prints one line to *stderr* and then generates a random HMAC key on
  every boot — silently orphaning every persisted lockout on each restart. Use the 32-byte form.
- **`TDAY_ENV` not exactly `production`.** No HSTS, no `Secure` cookie flag, and
  `REQUIRE_ENCRYPTION_AT_REST` is ignored. This is the single highest-impact typo in the file.
- **The key sits next to the data.** `DATA_ENCRYPTION_KEY` is in `.env.docker` on the same host as
  the Postgres volume. This protects a stolen dump, a detached volume or an offsite backup. It does
  **not** protect against anyone with shell access to the host.
- **`CSP_CONNECT_EXTRA` replaces rather than appends** — setting it drops the auto-derived Sentry
  ingest origin.

## 7. Verify after deploying

```bash
# Headers — CSP and Permissions-Policy should now be present
curl -sI https://<your-host>/ | grep -iE 'content-security-policy|permissions-policy|strict-transport'

# CORS still rejects a foreign origin
curl -s -o /dev/null -w '%{http_code}\n' \
  -H 'Origin: https://evil.example.com' https://<your-host>/api/auth/csrf   # expect 403

# The backend is bound to loopback, not every interface
ssh <user>@<deploy-host> "docker port tday_backend 8080"                    # expect 127.0.0.1:2525

# Rate limiting returns a real 429 with Retry-After, not a 500
for i in $(seq 1 6); do
  curl -s -o /dev/null -w "%{http_code} " -X POST https://<your-host>/api/auth/callback/credentials \
    -H 'Content-Type: application/json' -d '{"username":"nonexistent-probe","password":"wrong"}'
done; echo
```

The last check locks that probe identity for a while — use a username that does not exist, never
your own.
